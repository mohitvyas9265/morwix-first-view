Morwix Product Specification

Notification / Notice Module

Release 1 — user flow, UX decisions, recipient targeting, screens, status model and future-release considerations.

School Management PlatformParents • Students • SchoolsRelease 1Proposed

1. Purpose

Release 1 should allow a school administrator to create and manage notices and target them precisely to classes and sections.

Core principle: use one flexible recipient-selection system rather than separate flows for all classes, a few classes, or arbitrary class/section combinations.

2. Release 1 Scope

Create Notice

Create, target, configure responses, review and publish or save as draft.

View Notices

Search, filter and open notices to see their complete details and responses.

Recipient Targeting

Support school-wide, selected-class, and class-specific section targeting.

3. Core Product Model

Notice = What

Title, description and the message.

Recipients = Who

The classes and sections that should receive it.

Schedule = When

Start and end dates for the effective period.

Response = What is expected

Whether recipients need to respond and which options are available.

5. Create Notice

Step 1 — Notice Details

FieldRequiredNotes
Notice TitleYesShort, meaningful title.
DescriptionYesMain notice content.
Start DateYesWhen the notice becomes effective.
End DateYesWhen it stops being active.

Step 2 — Response

Use “Response Required?” instead of a generic “Type” field.

  • No — informational notice only.
  • Yes — configure response options.
Release 1 example: Agree / Approve and Disagree / Decline.

Step 3 — Recipients

Use a recipient builder.

Who should receive this notice?

○ All Classes

○ Selected Classes

If Selected Classes

☐ Class 1   ☐ Class 2   ☑ Class 6   ☑ Class 7   ☐ Class 8   ☑ Class 10

Step 4 — Per-Class Section Selection

Each selected class independently targets all sections or specific sections.

ClassTargeting
Class 6All Sections
Class 7Specific: A, C
Class 10Specific: B
This supports Class 6 → all sections, Class 7 → A/C, Class 10 → B in one workflow.

Terminology

Avoid “Random” in the UI. Use “Selected Classes” and “Specific Sections”.

6. Recipient Summary & Safety Check

Before publishing, show a clear summary of who will receive the notice.

Recipient Summary
Class 6All sections
Class 7Section A, C
Class 10Section B

Total recipients: 428 students / 428 parents (illustrative)

This is an important safety mechanism: administrators should verify targeting before publishing.

7. Review & Publish

Do not make the final action simply “Create Notice”. Use a review step.

Create/Edit → Save Draft OR Review Notice → Publish

The review screen should show title, description, dates, complete recipient summary, response requirement and response options.

Actions: Back & Edit / Publish Notice.

11. Status Model

StatusMeaning
DraftCreated but not published.
ScheduledOptional: published with a future start date.
ActiveCurrently within its effective period.
ExpiredEnd date has passed.
If Release 1 has no future start dates, simplify to Draft → Active → Expired.

12. Future Releases

ReleasePossible Enhancements
Release 1Basic notices, recipient builder, responses, filters, drafts/statuses.
Release 2Edit/archive, scheduling, read/unread tracking, notification history, improved recipient management.
Release 3Attachments, images/documents, rich text, recurring notices, templates, richer response types.
Release 4+Automated notifications triggered by school events and broader communication capabilities.

13. Design Decisions to Preserve

  1. One recipient-selection mechanism.
  2. Section selection is per class.
  3. Call the targeting area “Recipients” or “Send To”.
  4. Use “Response Required?” rather than “Type”.
  5. Use “Selected Classes” rather than “Random Classes”.
  6. Show a recipient summary before publishing.
  7. Use a Review & Publish step.
  8. Keep the View Notices table concise.
  9. Make filters independently combinable.
  10. Do not over-engineer Release 1.
